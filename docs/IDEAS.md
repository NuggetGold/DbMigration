# DbMigration — Идеи развития продукта

> Документ продуктового визионера. Описывает **дополнительные** фичи и улучшения поверх
> обязательных F1–F10 из `docs/SPEC.md`. Кода здесь нет — только идеи, ценность, оценка
> трудозатрат и риски. Все идеи рассчитаны на текущий стек: **C# / .NET 10 / WinForms**
> (WinForms-часть) + `DbMigration.Core` (net10.0) и доступные пакеты
> (`Microsoft.Data.Sqlite`, `MySqlConnector`, `Npgsql`, `Microsoft.Data.SqlClient`,
> `System.Security.Cryptography.ProtectedData`, `MSTest`).

## Как читать оценки

- **S** — небольшая, локальная работа (≈ несколько часов – 1–2 дня).
- **M** — заметная фича (≈ 3–7 дней): новый поток UI + логика в Core.
- **L** — крупная подсистема (≈ 1.5–3 недели): фоновая инфраструктура, несколько экранов,
  значимое тестирование.

Легенда столбцов у каждой идеи: **Питч** (что это), **Польза**, **Трудозатраты**, **Риск /
зависимости**, **В тёмной теме и glow** (как встроить в палитру opencode и эффект светящегося
текста).

## A. Инспекция и понимание схемы

### 1. Schema Diff — визуальный диф схем источника и цели
- **Питч:** Экран, который сравнивает схемы двух профилей и показывает, чем они отличаются:
  таблицы добавлены/удалены, колонки, типы, nullability, ключи, индексы.
- **Польза:** Перед миграцией видно реальную картину расхождений; ловятся сюрпризы (лишние
  NOT NULL, суженный VARCHAR) до записи в целевую базу. Отчёт «что изменится» продаёт
  инструмент как управляемый, а не «пальцем в небо».
- **Трудозатраты:** M–L. Опирается на `GetSchemaAsync` и уже готовые `TableSchema`/
  `ColumnSchema`; основная работа — сопоставление и UI.
- **Риск / зависимости:** Нормализация имён (регистр, схема) требует аккуратной логики; нужен
  фильтр «шумовых» системных таблиц. Никаких новых пакетов.
- **В тёмной теме и glow:** строки-различия подсвечиваются семантическими цветами
  (`Success` = совпало, `Warning` = изменилось, `Error` = удалено/опасно); у заголовка отчёта
  `ShineEnabled = true`, а количество расхождений — `GlowLabel` цвета `Warning`.

### 2. ER-диаграмма связей (граф таблиц и внешних ключей)
- **Питч:** Интерактивная диаграмма «сущность–связь»: узлы-таблицы и стрелки по
  `ForeignKeySchema`, с раскладкой и зумом.
- **Польза:** Мгновенно понятна структура незнакомой БД; помогает выбрать порядок миграции и
  увидеть циклы FK. Отличный «вау»-экран для демонстрации.
- **Трудозатраты:** L. Собственный layout-движок (force-directed или слоистый) на
  `System.Drawing`, пан/зум, hit-testing.
- **Риск / зависимости:** Могло бы понадобиться библиотека раскладки, но её нет в разрешённых
  пакетах — значит, пишем простой собственный алгоритм (риск «паутины» на больших схемах,
  нужен фильтр по глубине связей).
- **В тёмной теме и glow:** узлы — `BackgroundElement`, выбранный узел светится `Primary`;
  стрелки — `BorderActive`, активный путь миграции подсвечивается бегущим «импульсом» по
  стрелке в такт `AnimationClock`; имя выбранной таблицы — мигающий `GlowLabel`.

### 3. Профайлер колонок и распределение данных
- **Питч:** По каждой колонке считает статистику: NULL-доля, distinct-значения, min/max,
  длина строк, а для чисел/дат — гистограмму распределения.
- **Польза:** Обоснованный выбор типов при конвертации, оценка объёма данных, поиск «мусорных»
  колонок. Профайлер — фундамент для нескольких идей ниже (типы, PII, производительность).
- **Трудозатраты:** M. Запросы `SELECT COUNT(*), COUNT(col), MIN, MAX, COUNT(DISTINCT ...)`.
- **Риск / зависимости:** `COUNT(DISTINCT ...)` дорогой на больших таблицах — нужен
  семплирующий режим и предупреждение о стоимости. Только стандартный SQL.
- **В тёмной теме и glow:** гистограмма рисуется градиентом `Info → Secondary`; высокий
  процент `NOT NULL`-нарушителей подсвечивается `Warning`, а индикатор «колонок без проблем» —
  `Success` с мягким свечением.

### 4. Аудит индексов: «чего не хватает» и «что не используется»
- **Питч:** Анализ индексов и FK: отсутствующие индексы на FK-колонках, дублирующиеся и
  избыточные индексы, рекомендации по добавлению/удалению.
- **Польза:** Ускоряет целевую базу после миграции и снижает объём. Для SQL Server/PostgreSQL
  можно опираться на статистику использования, для остальных — на эвристики.
- **Трудозатраты:** M. Эвристики работают везде; «использование» — только там, где есть DMV/
  `pg_stat_user_indexes`.
- **Риск / зависимости:** Разные движки дают разную мета-информацию; нужен честный фолбэк.
- **В тёмной теме и glow:** карточки-рекомендации: «нужен индекс» — `Warning`, «дубликат» —
  `Error`, «ок» — `Success`; счётчик сэкономленных индексов мигает акцентом.

### 5. Глобальный поиск по схеме (fuzzy-find таблиц и колонок)
- **Питч:** Одно поле: «найди таблицу или колонку» по всей схеме, с нечётким поиском и
  переходом к нужному объекту.
- **Польза:** Резко ускоряет навигацию в больших БД; база для Command Palette (идея 15).
- **Трудозатраты:** S–M. Индекс имён в памяти + простой scoring.
- **Риск / зависимости:** Зависимостей нет; важно не блокировать UI на больших схемах.
- **В тёмной теме и glow:** совпавшие подстроки подчёркиваются `Primary`; при вводе заголовок
  поиска мягко пульсирует, а «нет результатов» — приглушённый `TextMuted` без свечения.

### 6. Side-by-side DDL-предпросмотр
- **Питч:** Для выбранных таблиц показывает точный `CREATE TABLE`, который будет выполнен в
  цели, рядом с исходным DDL, с подсветкой синтаксиса.
- **Польза:** Снимает главный страх миграции — «а что именно произойдёт». Готовый артефакт для
  ревью DBA; можно скопировать/сохранить.
- **Трудозатраты:** M. `BuildCreateTableSql` уже даёт целевой DDL; исходный — через метаданные
  или `sqlite_master`/`information_schema`.
- **Риск / зависимости:** Оригинальный DDL не всегда доступен «как есть» у всех движков —
  приемлемо показывать реконструированный.
- **В тёмной теме и glow:** панели на `BackgroundElement`; заголовок «Target DDL» с
  `ShineEnabled`; ключевые слова подсвечиваются `Primary`, типы — `Secondary`.

### 7. Dry-run (симуляция) миграции
- **Питч:** Полный прогон миграции «в холостую»: строит план, считает строки, проверяет
  совместимость и оценки времени, но **ничего не пишет** в цель.
- **Польза:** Уверенность до необратимого шага; обнаруживает блокеры (типы, ключи, права) и
  даёт ETA. Профессиональная фича, отличающая инструмент от «скрипта».
- **Трудозатраты:** M. Переиспользует `GenerateSqlScriptAsync` и профайлер/диф.
- **Риск / зависимости:** Оценка времени по объёму и throughput неточна — показывать диапазон.
- **В тёмной теме и glow:** бейдж «DRY-RUN» мигает `Secondary`; при отсутствии блокеров —
  зелёная галочка со свечением, при блокерах — красная иконка + список причин.

## B. Конвертация типов

### 8. Менеджер пользовательских маппингов типов
- **Питч:** Редактор правил «CanonicalType/нативный тип источника → нативный тип цели» с
  переопределением дефолтов и сохранением профилей маппинга.
- **Польза:** Спасает там, где автомаппинг ошибается (`DATETIME` vs `TIMESTAMPTZ`,
  `TEXT` vs `NVARCHAR`). Повторяемость между миграциями — правило один раз, применяется всегда.
- **Трудозатраты:** M. Опирается на `MapToNativeType`; нужна надстройка правил над дефолтом.
- **Риск / зависимости:** Требует, чтобы Core умел принимать кастомный словарь — возможно
  расширение контракта (согласовать с владельцем Core, контракты помечены как «замороженные»).
- **В тёмной теме и glow:** таблица правил: переопределённые строки светятся `Accent`;
  «сохранено» — мгновенный зелёный flash на заголовке через `GlowLabel`.

### 9. Советник по совместимости и lossy-предупреждения
- **Питч:** Предупреждает о потенциально «потерянных» преобразованиях: сужение длины,
  усечение точности `DECIMAL`, потеря timezone, конвертация BLOB↔TEXT.
- **Польза:** Предотвращает молчаливую потерю данных — самое дорогое, что может случиться при
  миграции. Даёт объяснение «почему это риск» и рекомендацию.
- **Трудозатраты:** M. Матрица пар (CanonicalType × CanonicalType) + данные профайлера
  (реальная max-длина, диапазон).
- **Риск / зависимости:** Ложные срабатывания снижают доверие — нужна калибровка и «я понимаю
  риск» чекбокс.
- **В тёмной теме и glow:** каждая потеря — строка `Warning`/`Error` с иконкой; заголовок
  «N потерь» пульсирует красным; безопасные преобразования — тусклый `TextMuted` (не отвлекают).

### 10. Auto-fix предложения для несовместимой схемы
- **Питч:** К каждому lossy-предупреждению — кнопка «исправить»: расширить тип, добавить
  default, разрешить NULL, привести значения (например, `DATETIME` для «битых» строк).
- **Польза:** Превращает отчёт-проблему в действие в один клик; экономит ручные правки DDL.
- **Трудозатраты:** M–L. Требует безопасного применения и предпросмотра diff.
- **Риск / зависимости:** Опасные автоправки — только с подтверждением и записью в аудит-лог
  (идея 12). Изменение значений может быть необратимым.
- **В тёмной теме и glow:** кнопка «Fix» подсвечивается `Primary`; применённые исправления
  коротко вспыхивают `Success`, нерешённые остаются пульсировать `Warning`.

### 11. Нормализация дат, времени и часовых поясов
- **Питч:** Явная стратегия обработки времени при миграции: сохранить как есть, привести к UTC,
  задать целевую timezone, сконвертировать `DATETIME ↔ TIMESTAMPTZ`.
- **Польза:** Устраняет классическую миграционную боль «все даты сдвинулись на N часов».
- **Трудозатраты:** M. Зависит от движка: PostgreSQL `TIMESTAMPTZ`, SQL Server `datetimeoffset`,
  MySQL/`DATETIME`, SQLite (текст/число юникс-времени).
- **Риск / зависимости:** Сложные правила DST и «наивные» даты; нужны тесты на переходах.
- **В тёмной теме и glow:** переключатель стратегии с иконкой часов; выбранная стратегия и
  предупреждение о сдвиге — `Info`/`Warning` с деликатным свечением.

## C. Безопасность и аудит

### 12. Обнаружение чувствительных данных (PII / секретов)
- **Питч:** Скан колонок по имени и по данным на предмет PII: email, телефон, паспорт/SSN,
  банковские карты (Luhn), пароли/токены по именам колонок.
- **Польза:** Управление рисками приватности; понимание, что именно «утекает» в копию базы.
  Критично для соответствия GDPR/PCI-DSS и для безопасной работы с продовыми данными.
- **Трудозатраты:** M. Регэкспы + семплирование значений; имён-эвристики.
- **Риск / зависимости:** Ложные срабатывания и стоимость сканирования больших таблиц
  (семплировать). PII-детекторы не абсолютны — позиционировать как «оценку».
- **В тёмной теме и glow:** найденные PII-колонки — красные бейджи с иконкой щита; счётчик
  «N чувствительных колонок» пульсирует `Error`, когда защита не включена.

### 13. Маскирование и токенизация при миграции (privacy-preserving)
- **Питч:** Опция «мигрировать с маскированием»: замена/хеширование/обратимая токенизация
  выбранных PII-колонок по пути в цель.
- **Польза:** Можно безопасно отдать копию базы разработчикам/аналитикам, сохранив структуру и
  связность (детерминированный псевдоним для FK).
- **Трудозатраты:** L. Детерминированное маскирование, сохранение связей, политики на колонку.
- **Риск / зависимости:** Обратимая токенизация требует хранилища ключей (DPAPI) и
  согласования; нельзя «сломать» уникальность. Обязательна запись в аудит-лог.
- **В тёмной теме и glow:** переключение «Raw / Masked» с цветом `Accent`; заголовок
  «MASKED MODE» мигает, показывая, что данные обезличены.

### 14. Полный аудит-журнал операций с экспортом и целостностью
- **Питч:** Неизменяемый журнал всех значимых действий (соединения, DDL/DML, миграции,
  бэкапы) с хеш-цепочкой для проверки целостности и экспортом в файл.
- **Польза:** Расследуемость («кто/когда/что изменил»), доказательная база для команды и
  комплаенса. Расширяет F8 из живого лога в постоянный аудит.
- **Трудозатраты:** M. Формат записи, хеш-цепочка, экран просмотра/фильтрации, экспорт.
- **Риск / зависимости:** Хеш-цепочка — не полноценная электронная подпись; честно называть
  «tamper-evident», а не «tamper-proof».
- **В тёмной теме и glow:** записи по уровню (`Info`/`Warning`/`Error`); бейдж целостности
  «chain OK» мягко светится `Success`, при разрыве — пульс `Error`.

### 15. Защита от опасных операций (guardrails)
- **Питч:** Перехват и подтверждение разрушительных действий: `DROP`, `DELETE`/`UPDATE` без
  `WHERE`, `TRUNCATE`, `DropAndRecreate` в SQL-консоли и миграции.
- **Польза:** Предотвращает катастрофические ошибки одним нажатием. Особенно ценно в консоли,
  где сейчас можно выполнить любой SQL.
- **Трудозатраты:** S–M. Парсер/детектор опасных паттернов + диалог «наберите имя таблицы».
- **Риск / зависимости:** Наивный парсинг SQL может ошибаться; лучше позиционировать как
  «best-effort» лишний барьер, а не гарантию.
- **В тёмной теме и glow:** диалог подтверждения — рамка `Error`, слово «ОПАСНО» пульсирует
  ярким свечением; безопасные запросы проходят без такого экрана.

### 16. Пароли и настройки окружения в одном защищённом хранилище
- **Питч:** Централизованное управление секретами подключений (уже DPAPI) + поддержка
  переменных окружения/подстановок (`${ENV:PG_PASSWORD}`) в профилях.
- **Польза:** Удобно и безопасно делиться профилями без паролей в открытом виде; CI/смена
  окружений без правки каждого профиля.
- **Трудозатраты:** S–M. Расширение `ConnectionProfile` (аккуратно с замороженными контрактами)
  и резолвер подстановок при построении строки подключения.
- **Риск / зависимости:** Нельзя логировать раскрытые секреты (уже есть `revealPassword`
  в `BuildConnectionString` — следить). Изменение профиля требует согласования.
- **В тёмной теме и glow:** поля-секреты отображаются точками; значок замка `Success` при
  защищённом хранении и `Warning`, если пароль хранится «небезопасно».

## D. Производительность миграции

### 17. Параллельная миграция таблиц (настраиваемая степень параллелизма)
- **Питч:** Копирование нескольких независимых таблиц одновременно, с лимитом воркеров.
- **Польза:** Кратный выигрыш на многотомных базах и серверных СУБД; в разы быстрее F4.
- **Трудозатраты:** L. Пул задач, per-table прогресс, агрегация в один `MigrationResult`.
- **Риск / зависимости:** Порядок FK (идея 18), соединения-на-поток, конкурентность цели;
  нужна осторожность с журналом прогресса из нескольких потоков.
- **В тёмной теме и glow:** отдельные прогресс-бары на таблицу с цветом `Secondary`;
  агрегированный throughput-график (идея 24) светится по мере роста.

### 18. Оптимизация порядка по FK-графу (топосортировка)
- **Питч:** Автоматический безопасный порядок миграции таблиц с учётом зависимостей; отложенные
  FK и их создание после загрузки данных.
- **Польза:** Устраняет ошибки вставки из-за нарушений FK и ускоряет bulk-загрузку.
- **Трудозатраты:** M. Топосортировка (алгоритм Кана) по `ForeignKeySchema` + обработка циклов.
- **Риск / зависимости:** Взаимные (циклические) FK требуют отложенного создания либо отключения
  проверок — движко-специфично.
- **В тёмной теме и glow:** визуализация очереди таблиц; текущая таблица подсвечивается
  `Primary`, ожидающая из-за FK — `TextMuted` с подписью «ждёт зависимости».

### 19. Возобновляемая миграция (checkpoint / resume)
- **Питч:** Периодические контрольные точки (по таблицам и по позиции), чтобы продолжить
  прерванную миграцию с места сбоя, а не с нуля.
- **Польза:** Спасает многогигабайтные миграции при обрыве сети/сбое; огромная экономия времени.
- **Трудозатраты:** L. Хранение состояния (в `IPersistence`-стиле), keyset-позиция, идемпотентный
  продолжатель.
- **Риск / зависимости:** Нужна корректная политика для уже вставленных строк и частично
  загруженных таблиц (`ExistingTableBehavior`); сложное тестирование.
- **В тёмной теме и glow:** бейдж «Resumed from checkpoint #N» акцентом; прогресс продолжает
  гореть с того же места.

### 20. Инкрементальная миграция по watermark
- **Питч:** Копировать только новые/изменённые строки по колонке-водяному знаку
  (`updated_at` / возрастающий ключ).
- **Польза:** Регулярная синхронизация без полного перелива; дешёвые повторные прогоны.
- **Трудозатраты:** M–L. Выбор watermark-колонки, хранение последней позиции, дедупликация.
- **Риск / зависимости:** Работает, только если есть подходящая колонка; не ловит физические
  удаления (нужен отдельный tombstone-подход).
- **В тёмной теме и glow:** подпись «incremental since <timestamp>» с иконкой; дельта-числа
  выделены `Secondary` со свечением.

### 21. Адаптивный batch size
- **Питч:** Автоматическая подстройка размера батча по фактическому throughput и памяти.
- **Польза:** Убирает ручной тюнинг F4; быстрее на серверах, безопаснее по памяти на слабых
  машинах/больших BLOB.
- **Трудозатраты:** S–M. Обратная связь по времени батча, ограничение по памяти.
- **Риск / зависимости:** Должен согласовываться с `MigrationBatchSize` из настроек как «старт».
- **В тёмной теме и glow:** текущий batch size в статус-строке меняет цвет при адаптации
  (`Info` → `Success`); стрелка тренда рядом.

### 22. Импорт CSV / JSON обратно в таблицу
- **Питч:** Обратная к F6 операция: загрузка CSV/JSON в таблицу с сопоставлением колонок и
  предпросмотром.
- **Польза:** Замыкает цикл «экспорт → обработка → импорт»; удобно для наполнения тестовых баз
  и переноса из файлов. Расширяет F6 до двунаправленного обмена.
- **Трудозатраты:** M. Маппинг заголовков, приведение типов, батч-вставка.
- **Риск / зависимости:** Разбор «грязного» CSV (кавычки, разделители, кодировки), ошибки
  конвертации — показывать построчно.
- **В тёмной теме и glow:** предпросмотр как grid с подсветкой проблемных ячеек (`Error`);
  успешный импорт — зелёная вспышка счётчика строк.

## E. UX / DX (удобство и скорость разработки)

### 23. Command Palette (Ctrl+K)
- **Питч:** Быстрый доступ ко всем действиям и объектам: «миграция», «новая вкладка SQL»,
  «открыть таблицу X», «бэкап» — через строку поиска.
- **Польза:** Опытные пользователи работают, не отрывая рук от клавиатуры; всё достижимо в пару
  нажатий. Сильно повышает «профессиональность» интерфейса.
- **Трудозатраты:** M. Реестр команд + fuzzy-поиск (общий с идеей 5) + оверлей.
- **Риск / зависимости:** Нужен единый реестр действий во всём UI; аккуратный фокус/клавиатура.
- **В тёмной теме и glow:** оверлей на подложке-затемнении; выбранная команда со свечением
  `Primary`, поле ввода с `PrimaryBright`-кареткой.

### 24. График прогресса и throughput в реальном времени
- **Питч:** Живой мини-график: строк/сек, ETA, обработанные байты, оставшееся время, память.
- **Польза:** Понятно, идёт ли миграция нормально или «зависла»; помогает при тюнинге.
- **Трудозатраты:** S–M. Отрисовка скользящего окна на `System.Drawing` из `MigrationProgress`.
- **Риск / зависимости:** Не перегружать UI-поток; обновлять не чаще FPS часов.
- **В тёмной теме и glow:** линия `Info → Secondary` с мягким свечением под графиком;
  локальные пики подсвечиваются `Primary`; «застой» отображается `Warning`.

### 25. Редактор SQL с подсветкой синтаксиса и автодополнением
- **Питч:** Улучшение F5: подсветка SQL, автодополнение имён таблиц/колонок из схемы, скобки,
  форматирование запроса.
- **Польза:** Консоль перестаёт быть «блокнотом»; меньше опечаток, быстрее пишутся запросы.
- **Трудозатраты:** M–L. Собственный рендер токенов поверх `RichTextBox`/custom-контрола;
  форматтер SQL.
- **Риск / зависимости:** Полноценный редактор — большой объём; можно начать с подсветки +
  автодополнения имён без полноценного парсера.
- **В тёмной теме и glow:** ключевые слова `Primary`, строки `Success`, числа `Secondary`,
  комментарии `TextMuted`; активная строка с тонкой подсветкой фона.

### 26. Мультивкладочность и восстановление сессии
- **Питч:** Вкладки для таблиц, SQL-консоли и отчётов; при перезапуске восстанавливается
  последняя рабочая сессия (открытые объекты, черновики запросов).
- **Польза:** Пользователь не теряет контекст между запусками; комфортная многозадачность.
- **Трудозатраты:** M. Табовая оболочка + сериализация состояния сессии в настройки.
- **Риск / зависимости:** Сериализация не должна сохранять секреты; аккуратно с замороженными
  контрактами (`AppSettings` можно расширять — владелец Core).
- **В тёмной теме и glow:** активная вкладка — `BackgroundElement` с акцентной полосой
  `Primary`; несохранённый черновик помечается мигающей точкой.

### 27. Undo/Redo и «грязная» индикация в редакторе данных (F3)
- **Питч:** Отмена/повтор правок ячеек и удаления/вставки строк до применения в БД; явная
  пометка несохранённых изменений.
- **Польза:** Безопасное исследование данных; защита от случайных правок «на живую».
- **Трудозатраты:** M. Стек операций, пакетное применение, транзакции.
- **Риск / зависимости:** Нужны транзакции для групп правок; осторожность с конкурентными
  изменениями.
- **В тёмной теме и glow:** изменённые ячейки подсвечены `Accent`; кнопки Undo/Redo активны/
  приглушены; счётчик изменений светится, пока не применён.

### 28. Шаблоны и сниппеты запросов
- **Питч:** Библиотека часто используемых SQL-шаблонов (создать индекс, найти дубли, топ-N по
  таблице) с подстановкой текущей таблицы в один клик.
- **Польза:** Ускоряет рутинные операции; делится best practice внутри команды.
- **Трудозатраты:** S–M. Хранилище сниппетов + простая подстановка плейсхолдеров.
- **Риск / зависимости:** Плейсхолдеры должны быть безопасны относительно инъекций имён —
  использовать `QuoteIdentifier`.
- **В тёмной теме и glow:** карточки сниппетов с иконками; выбранный подсвечивается `Primary`
  и лёгким свечением.

## F. Визуализация и работа с большими объёмами

### 29. Виртуализованный грид для миллионов строк
- **Питч:** Рендеринг только видимых строк (virtual mode) вместо материализации страницы в
  контрол.
- **Польза:** Плавная работа на огромных таблицах даже при больших страницах; меньше памяти.
- **Трудозатраты:** M. `DataGridView` в virtual mode + потоковая подкачка окна строк.
- **Риск / зависимости:** Нужна серверная/keyset-пагинация (идея 30), чтобы не тянуть всё; UI
  не должен блокироваться.
- **В тёмной теме и glow:** грид остаётся `BackgroundElement`/чередование строк; загрузка
  «хвоста» показывает тонкий пульсирующий индикатор `Secondary`.

### 30. Keyset-пагинация вместо OFFSET
- **Питч:** Быстрый листатель по большим таблицам через «после последнего ключа» вместо
  `OFFSET`, который тормозит глубоко.
- **Польза:** Перелистывание остаётся быстрым на любях глубине; база для виртуализации.
- **Трудозатраты:** M. Нужен ключ сортировки (PK); порядок и направление.
- **Риск / зависимости:** Требуется стабильный уникальный ключ; таблицы без PK — фолбэк к
  OFFSET с предупреждением.
- **В тёмной теме и glow:** индикатор «keyset: PK(id)» с иконкой; предупреждение о фолбэке —
  `Warning`.

### 31. Просмотрщик BLOB и JSON с подсветкой
- **Питч:** Красивый просмотр бинарных и JSON-значений: hex-вьюер, определение MIME
  (изображение/текст), pretty-print JSON с подсветкой.
- **Польза:** Данные в `Blob`/`Json`-колонках перестают быть «мусором» — их можно понять не
  выгружая наружу.
- **Трудозатраты:** S–M. Hex-дамп, эвристика MIME, JSON-рендер.
- **Риск / зависимости:** Большие BLOB — ленивый просмотр/предупреждение о размере.
- **В тёмной теме и glow:** JSON-ключи `Secondary`, значения по типу; изображения на тёмной
  подложке; hex — моноширинный с подсветкой «печатаемых» байтов `Success`.

### 32. Стриминговый экспорт/импорт без загрузки в память
- **Питч:** Экспорт и миграция потоково (forward-only reader → writer), без материализации
  таблицы целиком.
- **Польза:** Возможность обрабатывать таблицы больше доступной памяти; предсказуемое потребление.
- **Трудозатраты:** M. `IAsyncEnumerable`-пайплайн уже частично есть (`ReadTableAsync`).
- **Риск / зависимости:** Уже частично заложено контрактом; основное — не накапливать буферы
  и корректно бэктпрешнить.
- **В тёмной теме и glow:** счётчик обработанных байт/строк со свечением; «memory stable» —
  зелёный индикатор.

## G. Отчётность

### 33. HTML-отчёт о миграции (самодостаточный файл)
- **Питч:** По итогам прогона — один HTML-файл со сводкой: таблицы, строки, время, ошибки,
  throughput, различия схем, предупреждения.
- **Польза:** Артефакт для команды/DBA, который можно приложить к тикету; повторяемая
  отчётность вместо скриншотов.
- **Трудозатраты:** M. Генерация HTML из `MigrationResult` + встроенный CSS.
- **Риск / зависимости:** Без внешних пакетов — рендерить вручную; экранирование значений.
- **В тёмной теме и glow:** отчёт оформлен в той же палитре opencode; в браузере glow можно
  эмулировать CSS-анимацией, в приложении — предпросмотр в «веб»-окне с тем же акцентом.

### 34. Сравнительный отчёт «до/после»
- **Питч:** Сопоставление количества строк и ключевых метрик источника и цели после миграции:
  совпало / разошлось / не проверено.
- **Польза:** Верификация результата — доказательство, что данные доехали целиком. Это то,
  что чаще всего просят в реальных миграциях.
- **Трудозатраты:** M. `GetRowCountAsync` по обеим сторонам + сверка по таблицам.
- **Риск / зависимости:** Точные подсчёты на больших таблицах дороги — опция «быстрая сверка»
  по приблизительным счётчикам.
- **В тёмной теме и glow:** «Verified» — зелёный со свечением; расхождения — красные пульсирующие
  строки; не проверенные — приглушённый `TextMuted`.

### 35. Экспорт отчёта в Markdown / JSON
- **Питч:** Тот же отчёт (идея 33/34) машиночитаемо: Markdown для тикета, JSON для CI.
- **Польза:** Автоматизация (GitHub Actions, скрипты), лёгкая вставка в документацию.
- **Трудозатраты:** S. Сериализация существующего `MigrationResult`/модели отчёта.
- **Риск / зависимости:** Версионирование схемы JSON, чтобы парсеры не ломались.
- **В тёмной теме и glow:** кнопки форматов с иконками; «Copied» — короткая зелёная вспышка.

## H. «Умные» помощники и автоматизация

### 36. Советник по миграции (эвристический ассистент)
- **Питч:** Собирает находки профайлера, diff, lossy-предупреждений и PII в единый список
  приоритизированных рекомендаций: «сделай A, потом B, не забудь C».
- **Польза:** Превращает набор экранов в понятный план действий; снижает порог входа новичка.
- **Трудозатраты:** M. Агрегация правил, приоритизация, понятные формулировки.
- **Риск / зависимости:** Без внешнего ИИ — это детерминированные правила; не переобещать
  «интеллект».
- **В тёмной теме и glow:** список-чеклист: выполнено `Success`, к действию `Warning`,
  критично `Error`; заголовок «Ready to migrate» светится, когда блокеров нет.

### 37. Health-check базы (целостность и «сироты»)
- **Питч:** Быстрые проверки: `PRAGMA integrity_check` для SQLite, битые FK (сироты), дубликаты
  по уникальным ключам, NULL в NOT NULL, пустые таблицы.
- **Польза:** Находит проблемы в источнике до миграции и «мусор» после; полезно и как ежедневный
  инструмент, не только для миграций.
- **Трудозатраты:** M. Набор запросов на движок + понятные отчёты.
- **Риск / зависимости:** Проверки дорогие на больших базах — семплирование и явный запуск.
- **В тёмной теме и glow:** «All healthy» — зелёное свечение; каждая проблема — карточка с
  цветом по критичности и иконкой.

### 38. Генератор тестовых данных (seeding)
- **Питч:** Заполнение таблицы правдоподобными данными по типам колонок (имена, email, даты,
  числа, FK-связность).
- **Польза:** Быстрое наполнение тестовых/демо баз; незаменимо для проверки миграций без прода.
- **Трудозатраты:** M. Генераторы по `CanonicalType`, соблюдение constraints/FK.
- **Риск / зависимости:** Уникальность и ссылочная целостность; предупреждение на проде.
- **В тёмной теме и glow:** прогресс генерации в реальном времени; «прод?» — красный бейдж
  с пульсацией предупреждения.

### 39. Планировщик бэкапов (по расписанию)
- **Питч:** Расписание для F7: ежедневный/почасовой экспорт + «загрузка» в облако, с хранением
  N последних копий.
- **Польза:** Автоматическая защита данных без ручных действий; ротация копий.
- **Трудозатраты:** M. Планировщик в приложении (таймер/Windows Task Scheduler) + ротация.
- **Риск / зависимости:** Приложение не должно требовать запуска — либо Windows Task Scheduler,
  либо честно позиционировать как «напоминание/ручной запуск»; облако всё ещё заглушка.
- **В тёмной теме и glow:** строка «next backup in …» со свечением; индикатор «свежий бэкап» —
  `Success`, «просрочен» — `Warning`.

### 40. Соглашение о миграции как файл-манифест
- **Питч:** Сохранение всего плана миграции (профили-ссылки, таблицы, маппинги типов,
  маскирование, batch, расписание) в переносимый файл — «миграция как код».
- **Польза:** Повторяемость и ревью: один файл можно положить в git, приложить к тикету,
  запустить в CI. Мост к «профессиональному» использованию.
- **Трудозатраты:** M. Сериализация плана + загрузка/валидация; без секретов (по `Id`/имени
  профиля).
- **Риск / зависимости:** Не хранить пароли; версионирование формата; согласование с
  замороженными контрактами.
- **В тёмной теме и glow:** карточка манифеста с чек-суммой; при загрузке — короткая вспышка
  `Primary` и список применённых правил.

## Топ-5 по мнению автора

1. **№34 — Сравнительный отчёт «до/после».** Даёт главную вещь, за которой приходят пользователи:
   *доказательство*, что данные доехали целиком. Реализуемо на существующем
   `GetRowCountAsync`/`MigrationResult`, а ценность — максимальная (доверие к инструменту).
2. **№3 — Профайлер колонок.** Он одновременно закрывает качество конвертации, PII-скан,
   тюнинг производительности и «умные» рекомендации. Одна фича-фундамент с очень широким
   эффектом; окупается многократно. Начать именно с него.
3. **№13 — Маскирование/токенизация при миграции.** Самая «продающая» премиальная возможность:
   безопасно отдать данные разработчикам. Отлично сочетается с профайлером и аудит-логом и
   выделяет продукт на фоне простых «копировалок».
4. **№19 — Возобновляемая миграция (resume).** Практическая боль №1 на реальных больших базах:
   сбой на 90% и всё заново. Хоть и L по трудозатратам, это то, ради чего инструменту доверяют
   тяжёлые миграции.
5. **№23 — Command Palette (Ctrl+K).** Дешёвая по трудозатратам фича с огромным влиянием на
   восприятие: превращает набор форм в быстрый профессиональный инструмент. Хорошо сочетается с
   поиском по схеме и легко «засвечивается» в тёмной теме.

> **Порядок внедрения (предложение):** сначала фундамент — №3 (профайлер), затем №7 (dry-run),
> №1 (diff) и №34 (сверка); параллельно дешёвые UX-победы №23/№5/№28; затем крупные №13/№19/№17
> по мере готовности Core.
