# DbMigration — Вердикт по идеям (`docs/IDEAS.md`)

> Строгая продукт-оценка. Источники истины: `docs/SPEC.md` (в частности §4–5 — замороженные
> контракты) и фактические файлы `src/DbMigration.Core/**`.
> Ресурсный контекст: **1 кодер UI**, обязательные F1–F10 ещё не закрыты, облако — заглушка.

## 0. Методика

- **Value (1–5)** — ценность для пользователя/продукта с учётом того, что основная задача —
  закрыть F1–F10.
- **Effort (1–5)** — трудозатраты: `1 = S`, `2 = S–M`, `3 = M`, `4 = M–L`, `5 = L`.
- **Risk (1–5)** — технический/продуктовый риск, в т.ч. риск **сломать замороженные контракты**.
- **Итоговый балл:** `Score = Value × 2 − Effort − Risk`.
- Критерий одобрения на итерацию: `Effort ≤ 3 (S/M)`, `Value ≥ 3`, `Risk ≤ 2`,
  **нет** изменений в `src/DbMigration.Core/Models|Abstractions|CoreServices.cs`, и нет
  зависимости от ещё не существующего фундамента.

Реальность кода на момент оценки: `CoreServices.CreateDefault` бросает `NotImplementedException`,
то есть Core ещё не реализован; App содержит только `MainForm` + Theme/Controls. Любая идея,
требующая новых методов в замороженных интерфейсах, оценивается как блокирующая.

## 2. Проверка на противоречия замороженным контрактам

Заморожено (SPEC §4–5): всё в `src/DbMigration.Core/Models/**` и `Abstractions/**`, а также форма
record `DbMigrationServices` в `CoreServices.cs`. Ниже — идеи, которые **в заявленном виде**
требуют правки этих контрактов.

| # | Идея | Конфликт | Почему |
|---|------|----------|--------|
| 8 | Кастомные маппинги типов | Да | Требует принимать пользовательский словарь в `MigrationRequest`/`MapToNativeType` — оба заморожены. |
| 11 | Нормализация дат/TZ | Да | Нужны хуки конвертации внутри пайплайна `IMigrationEngine`/`MigrationRequest` (заморожены). |
| 13 | Маскирование/токенизация | Да | Нужна политика на колонку в `MigrationRequest` + хранилище ключей; контракт заморожен, объём L. |
| 16 | ENV-подстановки в профилях | Да | Идея явно предлагает расширить `ConnectionProfile` (заморожен). |
| 20 | Инкрементальная миграция | Да | Нужен фильтр/`WHERE` в `MigrationRequest` — заморожен. |

**Пограничные (можно реализовать без правки контрактов, но идея предлагает их менять):**

- **26 — Мультивкладки/сессия:** сохранение состояния требует расширения `AppSettings`
  (заморожен). Можно вынести сессию в отдельный App-side файл — тогда конфликта нет.
- **40 — Манифест:** если опираться на собственный DTO, конфликта нет; но перечисляет
  маппинги/маскирование, которых пока не существует.
- **18 — FK-топосортировка:** технически можно задать порядок через `MigrationRequest.Tables`
  (App-side), но гарантия корректности зависит от того, уважает ли движок порядок — формального
  конфликта нет, есть зависимость.

**Вывод:** идеи 8, 11, 13, 16, 20 не могут быть выполнены «сейчас» без согласования с
владельцем Core и разморозки контрактов. Это отдельный трек, не UI-итерация.

## 3. APPROVED FOR THIS ITERATION (реализовать сейчас)

Только S/M, высокая ценность, низкий риск, **без** изменений в замороженных контрактах.

1. **#5 — Глобальный поиск по схеме (S–M).** Строит in-memory индекс имён из `GetSchemaAsync`,
   даёт переход к таблице/колонке. Риск минимален, высокая польза на больших схемах, делит
   инфраструктуру fuzzy-поиска с #23. Контракты не трогает.
2. **#7 — Dry-run миграции (M).** «Холостой» прогон: план + `GenerateSqlScriptAsync` +
   `GetRowCountAsync`, без записи в цель. Максимальная ценность (снятие страха необратимости),
   использует **уже существующие** методы Core. Опорная фича для демо.
3. **#15 — Guardrails (S–M).** Детектор опасных паттернов (`DROP`/`TRUNCATE`/`DELETE`/`UPDATE`
   без `WHERE`, `DropAndRecreate`) перед `ExecuteNonQueryAsync` и перед миграцией. Обёртка над
   существующим вызовом; прямо снижает риск F5 (консоль выполняет любой SQL). Дёшево и полезно.
4. **#23 — Command Palette (Ctrl+K) (S–M).** Реестр действий поверх готовых форм; клавиатурный
   доступ ко всему. Чистый UI, нулевой риск для Core, сильный эффект на «профессиональность».
5. **#34 — Сравнительный отчёт «до/после» (M).** Сверка `GetRowCountAsync` источника и цели
   после миграции. Даёт главное, за чем приходят пользователи — **доказательство** полноты
   переноса. Контракты не трогает; топ-приоритет автора идей и мой.
6. **#35 — Экспорт отчёта в Markdown/JSON (S).** Сериализация `MigrationResult`/отчёта сверки.
   Самый дешёвый пункт, замыкает #34 в артефакт для тикета/CI. Минимальный риск.

**Суммарный эффект:** 2 фичи доверия к миграции (#7, #34), 1 безопасность (#15), 2 UX-победы
(#5, #23) и 1 дешёвая отчётность (#35). Ни одна не требует разморозки контрактов.

## 6. Финальные рекомендации

1. **Приоритет — F1–F10.** Идеи не должны вытеснять обязательные фичи; одобренные штуки должны
   встраиваться как «тонкий слой» поверх уже строящихся экранов (например, #23/#5 — поверх
   навигации, #7/#34/#35 — поверх F4, #15 — поверх F5).
2. **Порядок внутри итерации:** сначала #15 (дёшево, снижает риск F5) → #23 + #5 (общий fuzzy-ядро,
   один заход) → #7 (опора на `GenerateSqlScriptAsync`) → #34 → #35.
3. **Ничего не менять в `src/DbMigration.Core/**`.** Все одобренные идеи — App-side. Любую
   контрактную правку (см. §2) выносить отдельным решением владельца Core.
4. **Не обещать «умный ИИ».** Все отложенные «советники» (#9/#12/#36) — детерминированные
   эвристики; позиционировать как «оценку».
5. **Бэклог после F1–F10:** #3 (профайлер) как фундамент → #9 → #18 → #33/#24. Крупные (#13/#19/#17)
   — только после закрытия контрактов и стабилизации Core.
6. **Проверять по критерию DoD** (SPEC §7): сборка без предупреждений, тесты, каждая фича
   достижима. Идеи, которые нельзя покрыть тестом офлайн, понижать в приоритете.
